## 📋 1. Problem Statement & Challenge Requirements

### 1.1 Problem Statement
Build a simple, robust multi-currency digital wallet application (**Multi-Currency Digital Wallet Application**) for **one simulated user** who holds wallets in multiple foreign currencies (e.g., `USD`, `EUR`, `GBP`, `SGD`, `IDR`).

The application integrates with the **Frankfurter API**—an open-source public foreign exchange rates service tracking European Central Bank (ECB) data with zero API key or registration requirements.

### 1.2 User Capabilities & Functional Scope
The application enables the simulated user to:
1. **Deposit Simulated Funds:** Add simulated balance into any designated currency wallet.
2. **Withdraw Funds:** Withdraw funds from a specific wallet, strictly guarded against overdrafts.
3. **Convert Between Currencies:** Convert funds from one currency to another using real-time exchange rates provided by Frankfurter API.
4. **Transfer Funds Between Wallets:** Transfer funds between wallets owned by the user (strictly 1:1 intra-currency transfers between sibling wallets/pockets).
5. **Inspect Balances:** View individual balances across all currency wallets along with an estimated total portfolio value in a base currency (`USD`).
6. **View Transaction History & Individual Transactions:** Browse a comprehensive immutable transaction audit ledger and inspect individual transaction details (including applied exchange rates, timestamp, and correlation references).
7. **Dynamic Sub-Wallet (Pocket) Creation:** Provision multiple custom sub-wallets/pockets per currency (e.g. *USD Main*, *USD Savings*, *IDR Daily*) to organize financial holdings.

### 1.3 Out-of-Scope (Explicit Non-Requirements)
- ❌ No real payment provider or payment gateway integrations required.
- ❌ No complex authentication, registration, or password hashing required (utilizes a simulated user session).
- ❌ No real banking APIs or KYC (Know Your Customer) regulatory workflows required.

### 1.4 UX Mental Model: "Currency Conversion" vs. "Fund Transfer"

To eliminate transactional ambiguity and align with modern digital banking paradigms (e.g., Wise, Revolut):

1. **Convert Between Currencies (Self FX Exchange):**
   - **User Intent:** The user exchanges balance between two distinct currency wallets owned by themselves to rebalance portfolio holdings.
   - **Interaction Paradigm:** **"You Convert (Sell)" ➔ [Live Mid-Market Rate & ⇄ Swap] ➔ "You Receive (Buy - Estimated)"**.
   - **Input Currency Semantics:** The entered transaction amount strictly represents the **Source/Debit Currency (Sell Amount)**. The credited amount in the target currency is dynamically previewed in real-time as `SellAmount * LiveExchangeRate` and rounded per the target currency's ISO decimal rules (e.g., 0 decimals for `IDR`, 2 decimals for `EUR/USD`).
   - **Visual Clarity Invariant:** The amount input field MUST display an explicit currency symbol prefix (`$`, `€`, `£`, `S$`, `Rp`) and an ISO code badge (`USD`) to guarantee zero ambiguity over which currency is being debited.

2. **Transfer Funds Between Wallets (Intra-Currency Movement):**
   - **User Intent:** The user dispatches funds between two pockets of the **identical currency** (e.g., *USD Main* to *USD Savings*).
   - **Interaction Paradigm:** **"From Pocket (Debit)" ➔ "To Pocket (Credit - Same Currency)"** with strict 1:1 financial math and zero exchange fees.

#### Value Objects & Enums:
- **Currency Code:** ISO 4217 three-letter code (`USD`, `EUR`, `GBP`, `SGD`, `IDR`).
- **TransactionType:**
  - `DEPOSIT`: Inbound simulated funds addition.
  - `WITHDRAWAL`: Outbound funds cash-out.
  - `CONVERT_OUT`: Source wallet debit during currency conversion.
  - `CONVERT_IN`: Target wallet credit resulting from exchange rate calculation.
  - `TRANSFER_OUT`: Outbound wallet-to-wallet transfer (debit).
  - `TRANSFER_IN`: Inbound wallet-to-wallet transfer (credit).

### 2.3 Core Business Invariants (Strict Guarantees):
1. **Strict Non-Negative Balance (`balance >= 0`):** A wallet balance can never drop below zero. Any withdrawal, transfer out, or conversion exceeding the available balance throws `InsufficientBalanceError` (HTTP 422).
2. **Strict Positive Amounts (`amount > 0`):** All financial operations require a strictly positive number greater than zero. Values `<= 0` or `NaN` throw `InvalidAmountError` (HTTP 400).
3. **Double-Entry & Correlation Atomicity:** Every transfer or conversion between two wallets creates paired ledger records (`_OUT` and `_IN`) bound by a single shared `referenceId` correlation identifier.
4. **Currency Precision & Rounding Safety:**
   - Standard fiat currencies (`USD`, `EUR`, `GBP`, `SGD`): 2 decimal places (cents).
   - Zero-decimal currencies (`IDR`): 0 decimal places (whole Rupiah).
   - Calculation utilizes high-precision float math with IEEE-754 epsilon guard before rounding to target currency scale.
5. **Frankfurter Exchange Rate Resilience:**
   - Rate requests query `https://api.frankfurter.dev/v2/rate/{base}/{quote}` with fallback to `https://api.frankfurter.app/latest?from={base}&to={quote}`.
   - Guarded with an in-memory cache (TTL 60s) to minimize network latency and prevent rate-limiting.
   - Equipped with an offline triangular arbitrage fallback matrix to withstand external network outages.

## 🔌 3. Interface & REST API Contracts

### REST API Endpoints Overview:
| Method | Endpoint | Description |
|---|---|---|
| `GET` | `/api/wallets` | Retrieve all wallets for simulated user with balances and portfolio total |
| `POST` | `/api/wallets` | Dynamically create a new sub-wallet (pocket) per currency |
| `POST` | `/api/wallets/[id]/deposit` | Deposit simulated funds into a specified wallet |
| `POST` | `/api/wallets/[id]/withdraw` | Withdraw funds from a specified wallet |
| `POST` | `/api/wallets/convert` | Convert funds between currencies using live Frankfurter rates |
| `POST` | `/api/wallets/transfer` | Transfer funds strictly 1:1 between sibling wallets of the same currency |
| `GET` | `/api/rates` | Query live exchange rate from Frankfurter (`?base=USD&quote=EUR`) |
| `GET` | `/api/transactions` | Query transaction ledger history with `walletId`, `type`, and limit filters |
| `GET` | `/api/transactions/[id]` | Inspect detail of an individual transaction by ID |
| `GET` | `/api/health` | Operational liveness & readiness health probe returning runtime signature |

### Standard Response Envelope:

{
  "success": true,

  "error": null,

    "timestamp": "2026-10-13T14:30:00.000Z"
