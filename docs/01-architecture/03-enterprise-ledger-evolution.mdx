This document outlines the **Tier-1 Core Banking Evolution Blueprint** for the Multi-Currency Digital Wallet engine. ---

## 🎯 1. Architectural Motivation & Evolution Strategy

In live coding challenges and early-stage MVPs, engineering teams typically implement a **Correlated Double-Entry Ledger** (our current model):
- A single `Transaction` table stores both sides of an inter-wallet mutation (`DEBIT` and `CREDIT`) bound together via a shared correlation identifier (`referenceId`).
- This keeps query latency sub-millisecond, ensures zero-dependency in-memory test execution (`<300ms`), and prevents unnecessary table JOIN locks in SQLite.

However, as transactional throughput scales to millions of concurrent ledger mutations across multi-tenant environments, production banking compliance mandates strict **Separation of Intent vs. Accounting Postings**, **Optimistic Concurrency Control (OCC)**, **Network Idempotency**, and **Decoupled FX Rate Audit Provenance**.

## ⚙️ 3. Core Enterprise Architectural Invariants

### 3.1 Separation of Business Intent vs. Accounting Postings
1. **The `TRANSACTIONS` Table (Business Event):**
   - Captures **what the user intended to do** (`type = 'TRANSFER'` or `'CONVERT'`), the participant wallets (`source_wallet_id`, `target_wallet_id`), the requested amounts, and the execution lifecycle state (`PENDING` ➔ `SETTLED`).
2. **The `LEDGER_ENTRIES` Table (Immutable Double-Entry Truth):**
   - Pure immutable accounting journal. It records strictly atomic debit and credit lines (`direction: DEBIT | CREDIT`) for each involved wallet.
   - Enforces point-in-time mathematical reconciliation via explicit `balance_before` and `balance_after` columns.
   - **Zero-Sum Ledger Guarantee:**
     For same-currency transfers: `SUM(amount WHERE direction = CREDIT) - SUM(amount WHERE direction = DEBIT) = 0`.

### 3.2 Optimistic Concurrency Control (OCC via `version`)
To guard against concurrent race conditions (e.g., dual clicks or simultaneous API requests draining a balance):
- The `WALLETS` entity maintains an integer `version` field.
- Database balance updates execute with conditional CAS (Compare-And-Swap) logic:
  ```sql
  UPDATE wallets 
  SET balance = balance - :debitAmount, version = version + 1 
  WHERE id = :walletId AND version = :currentVersion;
  ```
- If rows affected equals `0`, a `ConcurrentModificationError` is thrown, triggering a retry or safe rollback.

### 3.3 Network Idempotency Guard (`idempotency_key`)
- In distributed microservice topologies, client retries over flaky networks can resend debit commands.
- The unique constraint `@@unique([idempotency_key])` on `TRANSACTIONS` guarantees that identical payloads received within the deduplication window return the cached original response without re-executing balance mutations.

### 3.4 Decoupled FX Conversion Auditing (`FX_CONVERSIONS`)
- Storing currency conversion rates as a dedicated 1:1 relation to the business transaction decouples exchange rate provenance (provider, rate date, quote timestamp, applied spread) from core ledger postings.
- Transfers executed within the same currency omit the `FX_CONVERSIONS` record entirely, keeping same-currency transfers 100% free of FX overhead.

```text
+----------------------------+-----------------------------------+-----------------------------------+
| Architectural Metric       | Current Implementation (MVP)      | Enterprise Evolution Target       |
+----------------------------+-----------------------------------+-----------------------------------+
| Primary Pattern            | Correlated Single-Table Ledger    | Normalized Multi-Table Ledger     |
| Persistence Model          | User, Wallet, Transaction (3 tbls)| 6 Normalized Tables               |
| Concurrency Control        | Domain Memory Guard (Unit Tests)  | Version Column Optimistic Lock    |
| FX Storage                 | Denormalized Columns on Tx        | Dedicated FX_CONVERSIONS Table    |

+----------------------------+-----------------------------------+-----------------------------------+
```
